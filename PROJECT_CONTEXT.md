# Project context

## Purpose and scope

Engineering Resources Hub (EngHub) is an open academic resource platform. Its first catalogue is for the University of Lagos (UNILAG), within the official Faculty of Engineering. The initial departments are Computer Engineering and Electrical and Electronics Engineering. Both programmes offer 100, 200, and 300 Level structures with First and Second Semester selections. The project owner validates course data; the seed/import workflow currently loads a reviewed Computer Engineering course CSV, including an explicit general-engineering classification for each row.

The repository is an npm workspaces monorepo and requires Node.js 24 or newer. The root package provides scripts for development, typechecking, builds, API tests, and Prisma database tasks.

## Workspace structure

- `apps/web`: React 19, TypeScript, Vite 7, React Router 7, TanStack Query, Tailwind CSS 4. The UI includes public Explore/Search, university, course, and resource discovery pages, linked department course rows, registration, email verification, login, sign-out, session restoration, an account dashboard with profile/academic details and status-filtered uploads, separate resource submission, post-verification onboarding with a required username, an authorized resource review queue, Super Administrator user/role management, and resource governance screens for deletion requests, reports, Trash, quarantine, restore, replacement, and history.
- `apps/api`: Express 5 and TypeScript REST API, mounted at `/api/v1`. Zod validates environment configuration and request data. The API has health/readiness checks, centralized error handling, academic endpoints, email-verified cookie-based authentication, optional academic/profile/preference read/write endpoints with relationship and field validation, role grants, resource ownership checks, scoped moderation, and resource governance endpoints.
- `packages/shared`: small TypeScript package exposed as `@erh/shared`; inspect its source before assuming what it exports.

Root commands include `npm run dev:web`, `npm run dev:api`, `npm run typecheck`, `npm run build`, `npm run test:api`, `npm run db:{generate,migrate,seed,studio}`, and `npm run auth:bootstrap-admin`.

## API behavior currently in the repository

- Health: `GET /health`, `/health/live`, `/health/ready`.
- Academic data: list universities; fetch a university with its faculty/department hierarchy; list faculties, departments, and programmes; fetch department/programme details; list courses with text search and university, faculty, department, level, session, semester, and pagination filters; fetch a course by UUID. Department-filtered course results also include courses whose code contains `GET` from that university, as general engineering courses available across its departments.
- Resources: create, search/list/filter, retrieve, update, and delete course-linked resources. Creation accepts validated multipart file uploads; local development storage, inline viewing, and download endpoints are implemented. New resources begin in `PENDING` status. Governance includes scoped deletion requests, reports, quarantine, recoverable Trash with scheduled purge/retry, restore, permanent purge, replacement uploads, audit history, and a reviewer inbox for new pending uploads, deletion requests, and reports. The inbox stores a per-user last-viewed timestamp. Super Administrators may approve their own resource submissions and deletion requests; moderators may not self-approve.
- Authentication: registration sends a one-time email verification link; verified users can log in and use current-user/CSRF/logout endpoints backed by bcrypt password hashes and opaque server-side sessions in HTTP-only cookies. Students, Contributors, and Super Administrators can submit; public resource access is limited to approved items; role assignment and moderation are scoped to the user's grants. Super Administrators can search/paginate users, grant/revoke roles, and review platform-wide resource submissions in the web app. Elevated role grants require the target account's email to be verified.
- Onboarding: users are signed in after email verification and then sent through account setup; a unique username is required to complete it. University, faculty, department, programme, level, semester, preferences, avatar URL, bio, and GitHub/LinkedIn URLs remain optional. API writes validate academic parent relationships, unique usernames, URL domains/protocols, and enumerated preference values. Public browsing does not require onboarding.
- Success responses use a `data` property; course lists also return pagination `meta`. Errors use an `error` object with a code and message.
- `apps/api/test` contains HTTP-level tests. Academic route tests mock Prisma so they do not require PostgreSQL.

## Access control

The initial six-role access policy is documented in `docs/AUTHORIZATION_POLICY.md`: Super Administrator (platform-wide), University Administrator (one university), Moderator (all of one university), Contributor (university-scoped resource contribution), Student (registered user who may submit resources), and Guest (anonymous public access). API enforcement is implemented for email-verified authentication, sessions, role grants, approved-only public visibility, uploader ownership, university-wide moderation, and self-moderation prevention for moderators. Super Administrators may approve their own resource submissions and deletion requests; moderators cannot approve their own submissions. The web app supports registration, email verification, login, session restoration, sign-out, optional onboarding, a protected account page, resource submission, and governance workflows. `Guest` is not a stored role. Password recovery, account suspension workflows, and academic-structure write APIs are not implemented.

## Data and database

Prisma is configured for PostgreSQL. The schema is in `apps/api/prisma/schema.prisma`; the generated client is configured at `apps/api/src/generated/prisma` and that generated directory is ignored by Git. The database adapter is `@prisma/adapter-pg` with `pg` and reads `DATABASE_URL`.

The implemented schema contains the academic and account models, `Resource`, `ResourceFile`, `ModerationAction`, `DeletionRequest`, `ResourceGovernanceEvent`, `ResourcePurgeJob`, `GovernanceInboxState`, and `ResourceReport`. Resources reference a course, optionally an academic session and semester, and optionally a legacy-nullable uploader for pre-auth records. Governance audit records preserve resource ID snapshots so history survives permanent purge. File metadata records a provider and storage key. Binary files use the `ResourceStorage` interface with local development storage in `.data/uploads` by default and an optional private Cloudflare R2 adapter selected with environment configuration. Existing local files can be copied and verified with `npm run storage:migrate-r2 --workspace @erh/api`; the command retains source copies. Direct presigned browser uploads, malware scanning, and failed-upload cleanup are future work. Governance migrations `20261124150000_resource_governance`, `20261124160000_resource_governance_event_cleanup`, and `20261124170000_governance_inbox_state` have been applied to the configured local PostgreSQL database; `npx prisma migrate status` reports the schema up to date. `apps/api/prisma/seed.ts` imports `docs/COMPUTER_ENGINEERING_COURSE_REVIEW.csv`, validates 36 Computer Engineering offerings for 100 and 200 Level, and upserts the UNILAG hierarchy. It also creates the Electrical and Electronics Engineering department, but current imported course rows target Computer Engineering.

Environment configuration uses `DATABASE_URL`, `API_PORT`, `WEB_ORIGIN`, `NODE_ENV`, `RESOURCE_STORAGE_DIR`, `RESOURCE_STORAGE_PROVIDER`, `RESOURCE_MAX_FILE_SIZE_BYTES`, and optionally the R2 endpoint, bucket, and access credentials. Local file storage is the default; the API can stream files to/from a private Cloudflare R2 bucket. Email verification uses `EMAIL_SMTP_URL` and `EMAIL_FROM`; production requires both, while development prints links to the API console if they are omitted. `.env.example` documents placeholders. Bootstrap admin credentials are runtime-only `BOOTSTRAP_ADMIN_*` variables for the one-time command; never store them in `.env.example`, notes, or source control.
